# Production `.env` — recommended values

No secrets in this file. This documents what `application/.env` should
contain on production (`kencomanufactur.co.id`) — it is created **once,
manually, directly on the server**, never committed, never generated by any
script in this repo. `scripts/deploy-production.sh` checks that this file
exists and that several of its values look sane, but it never creates,
overwrites, or prints it.

```env
APP_NAME="PT. Kenco Manufactur Indonesia"
APP_ENV=production
APP_KEY=                          # generate with artisan key:generate, see below — MUST be unique from staging, never copied from staging or local
APP_DEBUG=false
APP_URL=https://kencomanufactur.co.id

APP_LOCALE=en
APP_FALLBACK_LOCALE=en
APP_FAKER_LOCALE=en_US

LOG_CHANNEL=stack
LOG_STACK=single
LOG_LEVEL=error

DB_CONNECTION=mysql
DB_HOST=<Hostinger-provided host, typically localhost>
DB_PORT=3306
DB_DATABASE=<production-specific database — never reuse the staging DB>
DB_USERNAME=<production-specific user>
DB_PASSWORD=<real secret, set directly on the server>

SESSION_DRIVER=database
SESSION_LIFETIME=120
SESSION_SECURE_COOKIE=true          # production is HTTPS-only
SESSION_ENCRYPT=false

CACHE_STORE=database
QUEUE_CONNECTION=sync               # no queue workload exists yet — see PHASE-11A1 audit; revisit if that changes

FILESYSTEM_DISK=local

MAIL_MAILER=log                     # see below — flip to a real SMTP mailer only when contact-form/job-application email delivery is actually wanted
MAIL_FROM_ADDRESS="noreply@kencomanufactur.co.id"
MAIL_FROM_NAME="${APP_NAME}"
```

## Differences from staging, deliberately

| Setting | Staging | Production | Why |
|---|---|---|---|
| `APP_ENV` | `staging` | `production` | `scripts/deploy-production.sh` refuses to run if this isn't exactly `production` — it's the first guard checked. |
| `APP_URL` | `https://staging.kencomanufactur.co.id` | `https://kencomanufactur.co.id` | Also guarded by the deploy script. |
| `APP_KEY` | its own key | its own, different key | See below — never share a key across environments. |
| `LOG_LEVEL` | `warning` | `error` | Production shouldn't accumulate warning-level noise in `storage/logs/laravel.log`. |
| Database | staging-only DB/user | production-only DB/user | Never let staging and production share a database. |

## Do not commit

None of the following may ever appear in this repository, in a commit, in a
GitHub Actions log, or in any file this script prints:

- `APP_KEY`
- `DB_PASSWORD`
- SMTP password
- SSH private keys
- GitHub Secret values

`scripts/deploy-production.sh` and `scripts/backup-production-db.sh` read
these out of the server's own `.env` at runtime and never echo them,
consistent with how `scripts/deploy-staging.sh` and
`scripts/backup-staging-db.sh` already handle staging's equivalents.

## `APP_KEY` — first-time setup

Generate it fresh, on production, after `.env` exists with everything else
filled in:

```bash
/opt/alt/php83/usr/bin/php /home/u518638233/domains/kencomanufactur.co.id/application/artisan key:generate
```

**Production's `APP_KEY` must be different from staging's.** They are
separate environments with separate encrypted sessions and, eventually,
separate encrypted data — sharing a key would mean a compromise of one
environment's key compromises the other, and offers no benefit. This is
exactly the mistake that caused the staging first-deployment 500 (missing
`APP_KEY`, documented in the staging deploy history) — do not repeat it,
and do not "fix" it by copying staging's key instead of generating a new
one.

## `PUBLIC_PATH` — not needed

Same conclusion as staging (see `docs/PHASE-11A2-STAGING-DEPLOYMENT.md`'s
"Public path audit" and `docs/STAGING-ENV.md`): the split
`application/` + `public_html/` layout does not require a `PUBLIC_PATH`
override or any other `bootstrap/app.php` change. Vite's manifest lookup
resolves correctly against `application/public/build/manifest.json`
because `scripts/deploy-production.sh` builds and verifies that file
exists there before ever touching `public_html/`.

## `QUEUE_CONNECTION=sync`

No background job workload exists in this application yet (see
`docs/PHASE-11A1-HOSTING-AUDIT.md`). `sync` runs jobs inline on the request
thread — correct for now. Revisit only if a real queued job is introduced.
